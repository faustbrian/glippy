# v0.5 Receiver Terminal Effects, 2026-08-20

## Decision

Infer a conservative terminal-effect summary for the receiver of an exact
method when selected local source proves the effect on every normally returning
path. Parameter-effect inference and cleanup-managed result inference may
consume that summary instead of special-casing method names such as `Shutdown`.

Selected local source now includes the root modules, reachable modules selected
by the active Go workspace, and reachable local filesystem replacements.
Downloaded dependencies and workspace modules outside the selected import graph
remain excluded. Effect source remains read-only, bounded by the existing
package, file, and byte limits, and ineligible as a diagnostic or fix target.

## Observable Contract

The receiver is the exact `go/types` receiver object from the method signature.
The existing bounded CFG effect walk proves a direct receiver `Close` or
propagates a statically resolved receiver method whose summary guarantees close.
Method values and method expressions use the same receiver identity. A helper
parameter may inherit the known receiver effect, so a cleanup callback can call
either `resource.Shutdown()` or a proven helper that delegates to it.

Conditional or asynchronous closure, observation-only methods, early returns,
receiver reassignment, aliases, address escape, unresolved recursion, dynamic
or interface dispatch, promoted methods on an outer receiver, and conflicting
package variants do not prove closure.
Unknown receiver summaries do not change the existing conservative fallback for
ordinary parameter calls. A receiver summary records source behavior only; it
does not imply that a `testing.T.Cleanup` callback has already executed, so
use-after-close rules continue tracking the live resource during the test.

Receiver summaries use stable package-qualified method identities across
independent loads. The native effect schema and persistent cache component
advance from version 6 to version 7. The digest includes every receiver
identity, known and always state, possible effect kinds, and independently
guaranteed effect kinds. Package variants must produce the same summary.

## Behavioral Evidence

The imported cleanup regression first reported the result returned by a helper
whose cleanup callback called `resource.Shutdown()`. A broader focused fixture
first reported eleven acquisitions rather than the expected eight. The fixed
state suppresses direct, receiver-delegated, method-expression, and
parameter-delegated shutdown cleanup while retaining exact diagnostics for
conditional, asynchronous, aliased, reassigned, escaped, observation-only,
early-return, and interface-dispatched methods.

A separate two-module workspace fixture first reported the caller acquisition
because effect loading admitted only the root module path. The fixed selection
loads the reachable workspace helper and suppresses the diagnostic. Unit
coverage proves stable cross-load identity, content-sensitive deterministic
digests, agreeing and disagreeing package variants, reachable workspace and
local-replacement selection, and downloaded-dependency exclusion.

## Cost And Adoption

Five complete one-iteration `resource-not-closed` package benchmark samples on
Go 1.26.6, Darwin arm64, and an Apple M4 Max measured 71.81-74.65 ms,
2,113,248-2,686,960 B/op, and 17,034-17,461 allocs/op. Package loading remains
the dominant cost; this is directional rule evidence rather than a portable
release budget.

Against `go-libraries/pkg/http-client` at
`0e0240b1fdcefaa73619b8d0a5d0dfc778d9e2f0`, the pre-change exact-rule run
reported 17 findings. The receiver and reachable-workspace implementation
reports 12 and removes exactly the five caller findings produced by
`newGoCircuitBreakerIntegration`, whose cleanup invokes the separately
versioned local workspace module's proven `Breaker.Shutdown` method. The twelve
retained findings remain outside this proof and were not silently reclassified.
The external repository head and pre-existing `pkg/prompts/go.sum` modification
were unchanged.

## Revisit Trigger

Revisit receiver alias tracking only when a repeated real pattern can preserve
object identity across mutation without optimistic closure. Revisit downloaded
dependency inference only with an explicit bounded provenance and source-trust
policy. Add configured receiver effects only if project contracts gain a stable
receiver syntax and signature-validation boundary.
