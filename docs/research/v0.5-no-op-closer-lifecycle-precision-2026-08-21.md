# v0.5 No-Op Closer Lifecycle Precision, 2026-08-21

## Decision

Classify one exact selected-module `Close() error` method as no-op only when
its complete implementation returns a field reached directly from its receiver.
`resource-not-closed` does not assign an ownership obligation to values of that
exact type, and `resource-used-after-close` does not treat its `Close` call as a
state transition. Advance the native effect schema and persistent-cache
component to `native-effects-v13`.

This is a source-proven lifecycle fact, not a consequence of method naming or
an ordinary known-borrow receiver summary.

## Observable Contract

The method must be the exact conventional `Close() error` method selected by
`go/types` from a locally selected source package. Its body must contain one
return statement and that return must be a direct receiver-field chain. Every
loaded package variant for the stable method identity must agree.

Returning nil, a package value, a computed expression, or a helper result stays
tracked. Receiver or global mutation, nested method calls, multiple statements,
missing source, dynamic dispatch, and package-variant disagreement also stay
tracked. This prevents the broader known-receiver-borrow fact from being used
as proof that lifecycle work is absent.

## Behavioral Evidence

The first focused regressions reported a field-returning no-op closer under
both resource rules. They retained diagnostics for receiver mutation, a nested
closer call, global mutation, and a helper call. The first implementation also
classified every `return nil` closer as no-op and erased established lifecycle
diagnostics; the affected regression suite rejected that boundary. The final
contract keeps `return nil` closers tracked and excludes only the exact
receiver-field form.

Stable cross-load identity, digest sensitivity, deep cloning, and agreeing and
disagreeing package variants have focused unit coverage. Generated rule
documentation records the same conservative boundary.

## Cost And Adoption

Five complete one-iteration package-analysis samples on Go 1.26.7, Darwin
arm64, and an Apple M4 Max measured:

| Rule | Time | Bytes | Allocations |
| --- | ---: | ---: | ---: |
| `resource-not-closed` | 72.01-77.98 ms | 2.14-2.72 MB | 17,108-17,557 |
| `resource-used-after-close` | 41.30-45.65 ms | 5.73-5.74 MB | 68,211-68,227 |

These are directional rule costs rather than portable release budgets.

Non-mutating exact-rule dogfood is clean on Glippy and
`go-libraries/pkg/prompts`. At external revision
`8409c3d568cc0b921aa271f6dc0cc6dcfcc40625`,
`go-libraries/pkg/http-client` retains one credible
`resource-not-closed` finding for `newTestDecompressionBody` and no
`resource-used-after-close` finding. The four `fakeResumeFile` findings are
removed because their exact `Close` implementation only returns
`file.closeErr`. The external revision and pre-existing dirty state remained
unchanged.

## Revisit Trigger

Extend the no-op proof only when another repeated real pattern has an exact
source contract that excludes mutation, calls, synchronization, and external
lifecycle work. Do not infer no-op behavior from method names, empty receiver
summaries, test filenames, type names, or interface shape.
