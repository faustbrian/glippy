# v0.5 Returned-Alias Cancellation Obligations, 2026-08-20

## Decision

Consume exact `returns-alias` project contracts when
`context-cancel-leak` evaluates an assignment to the tracked cancellation
function. A result assigned back to the same cancellation variable returns
ownership to the caller and MUST keep the outstanding invocation obligation
live.

This extends the existing returned-alias lifecycle contract without introducing
an alias graph or raising the rule above its shared control-flow tier.

## Observable Contract

The rule recognizes direct one-result and tuple-result assignments, exact
result and argument indexes, method-expression receiver offsets, positional
multi-RHS assignments, and the final left-to-right write when one statement
targets the cancellation variable more than once. A direct final self-write
also preserves the obligation because it does not replace or transfer the
tracked value.

A guaranteed cancellation-invocation effect discharges the obligation even
when the helper also declares generic ownership transfer and returns the same
value. An uncontracted helper, a final replacement binding, a result assigned
to another binding, and dynamic or ambiguous calls retain the prior
conservative use-or-transfer behavior.

Only assignments that target the tracked cancellation variable use the shared
obligation classifier. Other references retain the admitted `lostcancel`
compatibility boundary, so this change does not reinterpret unrelated reads,
returns, closure captures, calls, or transfers.

## Behavioral Evidence

The package-level regression covers a single result, both zero and nonzero
tuple-result indexes, an ordinary positional multi-RHS assignment, an imported
same-module helper, a method expression, a duplicate target whose final source
is the returned alias, and a duplicate target whose final source is the
original value. Before the rule consumed assignment identity, the initial five
acquisition cases produced no diagnostics. The final fixture reports all eight
outstanding obligations.

Negative cases cover an identical uncontracted helper, guaranteed invocation
combined with transfer and returned identity, a returned alias overwritten by
a later replacement, the alias assigned only into another binding, a tuple
that returns the tracked alias while also creating a second alias binding, and
a dynamic method-value call. A separate red regression reproduced three false
positives when a preserving assignment also contained a blank, address, or
independent reference to the cancellation variable; those references retain
the admitted `lostcancel` use-or-transfer behavior. Existing
`context-cancel-leak` tests continue to cover discard, path joins, defer,
return, capture, no-return, generated-source, type-error, suppression, and
baseline behavior.

## Cost And Adoption

Five complete one-iteration package-analysis samples over 100 configured
cancellation aliases on Go 1.26.6, Darwin arm64, and an Apple M4 Max measured a
76.75 ms median, 4,054,064 B/op, and 43,300 allocs/op. The observed timing
range was 74.26-77.19 ms. This is directional regression evidence rather than
a portable latency budget.

Non-mutating exact-rule dogfood completed without findings on Glippy and on
`go-libraries/pkg/prompts` at
`59252704b2bcbcfba4c390519ffb94c5870c01f8`. Both runs used one freshly built
working-tree binary with ordinary analysis network access disabled. The
prompts repository's pre-existing dirty state and `go.sum` digest
`5682cca758f3e1cc9931b18bccfe7111dc56825dc8e8a4549e4171a0ca46db4b`
remained unchanged.

## Revisit Trigger

Revisit new alias bindings only when real cancellation leaks justify a bounded
dynamic alias representation that remains sound across reassignment, closure
capture, asynchronous execution, joins, and escape.
