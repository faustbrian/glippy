# v0.5 Bounded Incremental Workspace Analysis, 2026-08-16

## Decision

The first persistent LSP workspace-analysis boundary is implemented. One
backend session reuses finalized typed results for unaffected open packages,
reloads a changed package, and invalidates cached open reverse dependants from
the canonical package graph.

The initial boundary was exact package-result reuse. The 2026-08-19 follow-up
below adds bounded same-package incremental type checking without retaining CFG
or SSA graphs after a package run, including bounded import-only typed discovery
for newly added imports. The 2026-08-21 follow-up reparses and re-typechecks
changed selected-module dependencies and their retained reverse closure before
rechecking the root package.

## Session Contract

- Compatible open files in one package still share one package load.
- Every package result records canonical root and transitive dependency package
  paths from the exact loaded graph.
- A changed or closed open package invalidates its own result and every cached
  result whose graph reaches that package.
- A new package group uses root paths retained by its typed attempt even when
  later validation fails. If that attempt has no trustworthy root identity, a
  metadata-only `go/packages` load resolves the root before reuse decisions.
  Only a failed, empty, or ambiguous typed and metadata result invalidates the
  complete project-root session.
- An unaffected result is rebound to the current complete workspace overlay,
  so later code-action validation never receives the stale overlay that
  originally produced the result.
- Failed, incomplete, or filesystem-unverifiable analyses are not retained.
- The session retains at most eight package results within a deterministic
  128 MiB accounted-memory budget and evicts least-recently used entries first;
  the typed graph session has an independent eight-entry, 128 MiB bound.
- Format-capable source is charged at sixteen times its exact bytes and compact
  dependency source at twice its bytes. The weight reflects their distinct
  retention classes without claiming to measure process RSS.
- One newest result may exceed the byte budget so a large active package remains
  usable, but it is retained alone.
- A newly added import absent from the retained graph may trigger one bounded
  exact-package types load. It never enables test variants, dependency syntax,
  or effect facts, and it uses `pattern=` escaping so import literals cannot be
  interpreted as package-query metapatterns.
- A changed active source in the main module, active workspace modules, or a
  local filesystem replacement may reuse the retained graph when package
  membership, build constraints, and module/workspace controls are unchanged.
  Glippy reparses the changed package, rechecks every retained reverse
  dependant needed by the selected root, and rebuilds selected-module effect
  facts before root diagnostics.

## Filesystem And Policy Invalidation

Before reuse, Glippy revalidates exact bytes for captured non-overlay package
sources and configured baseline content. It also revalidates Go-file directory
membership plus `go.mod`, `go.sum`, `go.work`, and `go.work.sum` beneath the
selected root. Configuration and semantic-contract contents already participate
in the package-group configuration digest; source language and maximum analysis
tier remain explicit group-key inputs.

This covers ordinary editor overlays, on-disk sibling changes, added or removed
Go files, package dependency edits represented by another open package, module
selection, configured contracts, and baselines without trusting modification
times.

For capable clients, the server dynamically registers bounded workspace
watchers for Go, module/workspace, configuration, and TOML/JSON policy inputs.
Created, changed, and deleted file notifications are normalized to sorted unique
absolute paths and recorded in the backend session before a new snapshot is
analyzed. Exact captured files and tracked Go-source directories identify the
affected package; the retained transitive package graph also invalidates open
reverse dependants while unrelated package results remain reusable. This
includes captured local dependency source outside the selected project root
when the client reports its change.

## Behavioral Evidence

Focused regressions prove:

- an edit reloads one of two unrelated open packages while the other result is
  reused;
- the reused result receives the new complete overlay;
- editing an open dependency invalidates its open reverse dependant;
- changing a closed sibling source, adding a Go file, or changing `go.mod`
  reloads the package;
- compatible same-package buffers remain batched;
- unrelated package and external-test-package failures remain isolated; and
- the bounded cache deterministically excludes its least-recently used
  entries.
- superseded document analysis is canceled, pending intermediate versions are
  debounced, and only the newest exact version publishes diagnostics.
- final-document close and stale-snapshot completion reject queued actions,
  drain pending shutdown, and retain explicit request-cancellation precedence.
- repeated shutdown cannot replace the request already waiting for analysis,
  and protocol write failures remain session errors.
- workspace watching is registered through the standard client capability,
  watched changes trigger one refreshed open-document snapshot, and the backend
  receives bounded canonical local paths; and
- a watched dependency file invalidates its package and open reverse dependant
  without reloading an unrelated open package, even when file bytes are
  unchanged between snapshots;
- the retained-byte budget evicts older results before a newer result, retains
  one oversized newest result alone, and charges analyzed source automatically;
- a typed-failing new dependency uses metadata-only discovery to invalidate its
  retained reverse dependant while preserving an unrelated cached package;
- typed attempts retain already-proven root paths through later validation
  failures, metadata discovery failure preserves root-wide invalidation, and
  cancellation remains an operation-level error; incompatible workspace
  buffers do not trigger discovery against substituted disk bytes;
- a nested package, changed main-module dependency, active workspace-module
  dependency, and local replacement source use the incremental path, while a
  changed replacement module or sum file still forces a full load;
- typed-session invalidation returns while a full package load is still active.

The red state performed two package loads after an unrelated edit. The fixed
state performs one.

The 2026-08-19 graph-first follow-up also removes root-wide invalidation when a
package group has no retained result. New groups are analyzed before reuse
decisions, and their exact returned root package paths invalidate only retained
entries whose root or dependency graph intersects those paths. Opening an
unrelated package therefore retains the known package result and performs only
the new package analysis. Opening a package that is a dependency of a retained
consumer still reloads that consumer. A failed or unidentified new graph falls
back to invalidating the complete selected root.

The metadata-only graph follow-up closes that unidentified-new-group boundary.
If a typed attempt fails before returning root paths, Glippy loads only package
names, file lists, imports, transitive dependency metadata, test ownership, and
module metadata under the same overlay, build, module, offline, and graph-limit
policy as typed loading. It does not request export data, syntax, types, type
information, type sizes, CFG, SSA, or facts. Exact discovered roots scope
reverse-dependant invalidation; ordinary discovery failures keep the existing
root-wide fallback, while cancellation propagates. An ill-typed overlay still
produces its package identity because this discovery does not type-check it.
If the exact workspace overlay cannot be constructed, discovery does not run
against stale disk bytes.

The same-package typed-session follow-up retains an independently bounded
compact type graph for each eligible result. A compatible overlay edit reparses
every compiled root source into a fresh file set and runs `go/types` with the
retained dependency packages as its exact importer. It then returns ordinary
package input to the unchanged types, CFG, SSA, effect, cache, suppression,
baseline, and LSP code-action engines. Dependency syntax and dependency
`types.Info` maps are never retained by this session.

The same boundary applies to packages nested beneath the selected project root.
Before reuse it validates active and ignored source, directory membership, and
module files for the root and mutable local dependencies, including workspace
modules and local module replacements outside that root. Toolchain and
immutable module-cache packages are not polled on every edit. A file
notification advances the typed-session generation and discards retained
graphs without waiting for an active full load; a concurrent load cannot
repopulate the invalidated generation.

The incremental path is deliberately narrower than the result-reuse path. It
requires one clean package root or a coherent family of base, internal-test,
and external-test roots; unchanged source membership, build constraints, and
project controls; no cgo-generated compiled source; and only imports already
present in the retained graph or resolved through the bounded import-only typed
loader. An overlay may replace an already selected active source in a mutable
local dependency, but may not introduce dependency source membership or build
selection changes. Families are rechecked in base, internal-test, then
external-test order so an external test imports the fresh internal variant.
Internal-only and external-only roots recheck their selected package-under-test
dependency from disk or overlay. A newly direct root import is admitted only
when Go internal/vendor visibility permits it. A new dependency import,
import-load failure, diagnostics, missing or ambiguous identities, parse or type
failure, a changed build constraint or ignored-file selection, any file
notification, a module/workspace-control change, a malformed or ambiguous test
family, and every uncertain identity use the complete loader. These fallbacks
preserve the current valid-source editor contract instead of manufacturing
partial package diagnostics.

## Performance Evidence

The owned benchmark changes one of two unrelated packages after warming both.
Three three-operation samples on an Apple M4 Max, Darwin arm64, Go 1.26.5,
`GOMAXPROCS=1`, measured:

| Sample | Time | Bytes/op | Allocs/op | Package loads/op |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 34.22 ms | 558,114 | 3,926 | 1.000 |
| 2 | 35.87 ms | 558,144 | 3,929 | 1.000 |
| 3 | 28.55 ms | 557,989 | 3,927 | 1.000 |

The host was not isolated, so these are directional focused measurements rather
than release thresholds. The exact one-load functional metric is the durable
regression contract.

After adding accounted-memory eviction, three new three-operation samples on
the same host and toolchain measured 51.96 ms, 30.66 ms, and 33.14 ms; each
performed exactly 1.000 package load per operation and allocated
565,042-565,216 bytes with 3,982-3,983 allocations. This preserves the durable
reuse contract. It does not establish a portable editor-latency or RSS budget.

The owned same-package benchmark alternates ten valid overlays after one warm
load. Three samples on the same Apple M4 Max reference host with Darwin arm64
and Go 1.26.6 measured 368.1, 368.8, and 484.2 microseconds per operation,
177,712-177,716 bytes, and 1,003 allocations. Every sample reported exactly one
incremental load and zero full primary package loads per operation. These are
focused directional timings; the zero-full-load metric is the durable behavior.

Focused package-session and LSP regressions prove that production edits with
internal tests, direct internal-test buffer edits, and repeated external-test
buffer edits perform one initial full load followed by incremental loads.
Clean-load comparison preserves the diagnostic code, range, and message.
Changing a test build constraint still forces a full load. An external test's
package-under-test overlay now rechecks incrementally. This is functional
evidence, not a new latency measurement.

The changed-dependency benchmark alternates an exported result type and the
matching consumer overlay after one warm load. Five ten-operation samples on
the same Apple M4 Max class of host with Darwin arm64 measured
618.5-663.6 microseconds per operation, 273,274-277,954 bytes, and
1,607-1,611 allocations. Every operation performed one incremental load and
zero full primary loads. These are directional timings; the durable contract
is fresh dependency types and byte-equivalent diagnostics without a full load.

The import-only typed-discovery regression starts from one clean package, adds
one previously unavailable standard-library import through an editor overlay,
and compares the resulting diagnostic code, range, and message with a clean
load. The red state performed two full primary package loads. The fixed state
performs one initial full load, one exact import-only load, and one incremental
load. A local-package regression proves that the discovered import remains in
the retained graph across a third edit. Focused failure and cancellation cases
prove full-load fallback and cancellation propagation, and special-looking
import paths prove exact query escaping. No new latency or RSS claim is made.

## Remaining Work

Eligible same-package overlay edits no longer run the complete primary package
loader, and their CFG and SSA representations rebuild from fresh root types.
New root imports can use bounded import-only typed discovery, and selected local
dependency source changes rebuild retained types and effects. Dependency import
graph changes, cgo-generated inputs, memory-aware worker scheduling, portable
editor latency/RSS budgets, and further interprocedural error and ownership
precision remain active v0.5 work.
