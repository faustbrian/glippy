# v0.5 Bounded Incremental Workspace Analysis, 2026-08-16

## Decision

The first persistent LSP workspace-analysis boundary is implemented. One
backend session reuses finalized typed results for unaffected open packages,
reloads a changed package, and invalidates cached open reverse dependants from
the canonical package graph.

This is exact package-result reuse. It is not same-package incremental type
checking and does not retain `go/types`, CFG, or SSA graphs after a package run.

## Session Contract

- Compatible open files in one package still share one package load.
- Every package result records canonical root and transitive dependency package
  paths from the exact loaded graph.
- A changed or closed open package invalidates its own result and every cached
  result whose graph reaches that package.
- A new or otherwise unidentified package group conservatively invalidates the
  complete project-root session before its graph identity is known.
- An unaffected result is rebound to the current complete workspace overlay,
  so later code-action validation never receives the stale overlay that
  originally produced the result.
- Failed, incomplete, or filesystem-unverifiable analyses are not retained.
- The session retains at most eight package results and evicts the least
  recently used entries deterministically.

## Filesystem And Policy Invalidation

Before reuse, Glippy revalidates exact bytes for captured non-overlay package
sources and configured baseline content. It also revalidates Go-file directory
membership plus `go.mod`, `go.sum`, `go.work`, and `go.work.sum` beneath the
selected root. Configuration and semantic-contract contents already participate
in the package-group configuration digest; source language and maximum analysis
tier remain explicit group-key inputs.

This covers ordinary editor overlays, on-disk sibling changes, added or removed
Go files, package dependency edits represented by another open package, module
selection, configured contracts, and baselines without trusting modification
times. A local dependency outside captured source and the selected root remains
conservatively dependent on a future workspace file-watching boundary.

## Behavioral Evidence

Focused regressions prove:

- an edit reloads one of two unrelated open packages while the other result is
  reused;
- the reused result receives the new complete overlay;
- editing an open dependency invalidates its open reverse dependant;
- changing a closed sibling source, adding a Go file, or changing `go.mod`
  reloads the package;
- compatible same-package buffers remain batched;
- unrelated package and external-test-package failures remain isolated; and
- the bounded cache deterministically excludes its least-recently used
  entries.

The red state performed two package loads after an unrelated edit. The fixed
state performs one.

## Performance Evidence

The owned benchmark changes one of two unrelated packages after warming both.
Three three-operation samples on an Apple M4 Max, Darwin arm64, Go 1.26.5,
`GOMAXPROCS=1`, measured:

| Sample | Time | Bytes/op | Allocs/op | Package loads/op |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 34.22 ms | 558,114 | 3,926 | 1.000 |
| 2 | 35.87 ms | 558,144 | 3,929 | 1.000 |
| 3 | 28.55 ms | 557,989 | 3,927 | 1.000 |

The host was not isolated, so these are directional focused measurements rather
than release thresholds. The exact one-load functional metric is the durable
regression contract.

## Remaining Work

Typed analysis of the changed package still runs the complete package loader
and rebuilds its type, CFG, SSA, and effect representations. The server also
still analyzes document notifications synchronously; it does not debounce or
cancel an analysis superseded by a later document version. Persistent reusable
typed graphs, reverse-dependency graph updates independent of an analysis run,
workspace file notifications, superseded-version cancellation, memory-aware
eviction, and portable editor latency/RSS budgets remain active v0.5 work.
