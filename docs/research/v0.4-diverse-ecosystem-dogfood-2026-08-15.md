# v0.4 Diverse Ecosystem Dogfood, 2026-08-15

## Scope

The v0.4 audit ran a development Glippy binary built from
`22e2a9deee3e7e57880b90e57ac9507cefad2343` plus the final precision and
package-fix batch against six pinned public repositories. The copies were
disposable and no upstream repository was modified or published.

| Workload | Revision | Role |
| --- | --- | --- |
| fzf | `bd4efa277b49ef34ca4025bff9b1a288e1980eff` | command-line application |
| Caddy | `50e54ee279aa1e504fe218ca49ab6ae16c100410` | HTTP server and plugin host |
| sqlc | `8a7cddfbb9088666eb981645285d7699e71dcb54` | database-heavy generator |
| NATS Server | `99bbfb98035f4f0df06333a9a280c0517eaeff1c` | concurrent network server |
| chi | `8b258c7bb28f97a5f2a856ff7ef962578fec9215` | public HTTP library |
| go-sqlite3 | `f9fc7aaf8779eaf4d274010f4b068da1990fd9ed` | cgo-heavy library |

fzf, chi, and go-sqlite3 required disposable Go 1.25 directive shims so the
development binary's supported-source policy could analyze them. Each target
used a disposable Glippy cache configuration. The shims and configuration are
test harness inputs, not proposed upstream changes.

## Diagnostic Outcomes

| Workload | Default | Suspicious | Pedantic | Performance |

| fzf | 0 | 57 | 29 | 0 |
| Caddy | 0 | 67 | 247 | 0 |
| sqlc | 0 | 355 | 49 | 0 |

| chi | 0 | 10 | 0 | 0 |
| go-sqlite3 | source error, 0 | source error, 47 | source error, 1 | source error, 0 |

All six default correctness selections produced zero Glippy findings. The
go-sqlite3 runs also produced ten cgo/source prerequisite diagnostics and exit
category 2; rule findings are reported separately above. This is a package
loading boundary, not a clean complete run.

No repository configuration suppressed or baselined a finding, so the
suppression rate was zero. The default-policy false-positive rate was also zero
because there were no default findings. The complete optional output was not
manually adjudicated and therefore has no claimed false-positive percentage.
Optional counts must not be read as confirmed defect counts. Reviewed samples
were used to find precision defects and credible unique bugs.

The final suspicious distributions were dominated by intentionally opt-in
obligation and ignored-error rules:

- fzf: 53 `discarded-error`, three `resource-not-closed`, and one
  `unchecked-scanner-error`;
- Caddy: 29 `discarded-error`, 29 `resource-not-closed`, five `defer-in-loop`,
  two HTTP body leaks, one scanner error, and one header-key finding;
- sqlc: 344 `discarded-error`, eight resource findings, and three scanner
  findings;
- NATS Server: 636 discarded errors, 169 loop defers, 125 resource findings,
  13 integer-division findings, 11 nilness findings, and two header-key
  findings;
- chi: eight discarded errors, one HTTP body leak, and one loop defer; and
- go-sqlite3: 24 resource findings, 11 overwritten errors, six rows errors,
  four loop defers, and two nilness findings.

## Defects Beyond Default Tooling

`go vet ./...` was clean for all six pinned inputs. Staticcheck
`2026.2rc1 (0.8.0-rc.1)` was run on every input with network access disabled.
It reported its own deprecation, unused-code, style, and semantic findings, but
did not report the reviewed fzf, Caddy, sqlc, or chi lifecycle findings below:

- fzf can terminate a network-backed scanner without observing `Scanner.Err`;
- Caddy has a panic-log scanner whose terminal error is unchecked;
- two Caddy HTTP error paths return without closing response bodies;
- a chi test goroutine leaks an HTTP response body; and
- three sqlc scanner paths can silently truncate input.

NATS also exposed impossible or stale error checks. Staticcheck independently
reported one always-true error comparison, so that occurrence is corroborating
rather than unique Glippy coverage. These samples establish additional value;
they do not imply that every optional diagnostic is absent from Staticcheck.

## Fix Rehearsals

| Workload | Selection | Applied | Files | Rejected | Second run |
| --- | --- | ---: | ---: | ---: | --- |
| fzf | safe redundant type | 1 | 1 | 0 | clean |
| fzf | unnecessary conversion | 15 | 7 | 0 | clean |
| Caddy | unnecessary conversion | 2 | 2 | 0 | clean |
| sqlc | needless blank identifier | 4 | 3 | 0 | clean |
| NATS Server | safe redundant type | 4 | 4 | 0 | clean |
| NATS Server | unnecessary conversion | 56 | 29 | 8 | same 8 rejected |
| chi | unnecessary conversion | 0 | 0 | 0 | clean |

Every applied result reparsed, formatted, passed typed validation, and reached
an idempotent second run. The eight NATS rejections are three files whose
existing comments fall outside the formatter's proven ownership model. Glippy
preserved the original bytes and reported the validation boundary instead of
forcing a suggestion. The rehearsal also exposed and corrected two
`unnecessary-conversion` false positives involving contextual untyped shifts
and defined boolean conversions. Optional-preset review also narrowed
`deferred-lock` to an adjacent lock/deferred-relock transposition, invalidated
nil-map facts when a map address escapes to possible initialization, retained
range-copy mutations whose modified value is later consumed, and omitted
cross-file related ranges that cannot be represented as one file-owned
diagnostic. Focused close negatives preserve each corrected boundary.

## Reference-Host Performance

Measurements used ordinary suspicious-policy lint on an Apple M4 Max running
Darwin arm64. Each cold/warm pair used a fresh Go build and Glippy analysis
cache for the cold run, then reused it for the warm run. Peak RSS is from
`/usr/bin/time -l`.

| Workload | Cold range | Warm range | Peak RSS range |
| --- | ---: | ---: | ---: |
| chi | 6.84-8.39 s | 1.15-4.57 s | 1.22-1.50 GB |
| fzf | 6.01-8.46 s | 1.09-2.83 s | 1.20-1.42 GB |
| Caddy | 21.06-25.46 s | 3.56-5.83 s | 5.42-6.32 GB |
| sqlc | 22.65-32.45 s | 4.40-10.32 s | 6.58-7.65 GB |
| NATS Server | 24.70-25.89 s | 6.42-8.19 s | 5.21-5.99 GB |
| go-sqlite3 | 16.57-17.52 s | 0.78-0.91 s | 0.82-0.87 GB |

go-sqlite3 exited with the documented cgo/source prerequisite category in all
samples. For this exact pinned corpus and reference host, the v0.4 development
budget is 40 seconds cold, 12 seconds warm, and 8 GiB peak RSS. Every sample is
inside that bounded budget. The 5-7.65 GB large-repository peaks are high and
must not be described as Clippy-like memory use; memory reduction remains a
priority for later releases.

## Result

The diverse corpus proves clean default policy, useful optional defect classes,
transactional and idempotent fixes, conservative formatter rejection, and a
bounded reference-host budget. It does not prove cgo completeness, low memory,
or a statistically representative false-positive rate for optional presets.
