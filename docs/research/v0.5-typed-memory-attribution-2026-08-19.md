# v0.5 Typed-Analysis Memory Attribution, 2026-08-19

## Decision

The next large typed-analysis memory owner is the dependency graph required by
the fact-bearing `printf-arguments` adapter. It is not SSA construction, CFG
retention, or ordinary rule findings.

Glippy now has an opt-in retained-heap phase observer and an external profiling
harness that writes garbage-collected heap profiles after package loading,
source-model construction, effect facts, each native analysis tier, adapted
analyzers, and final result assembly. Ordinary CLI and LSP runs do not install
an observer and retain their existing behavior.

## Workload

- Host: Apple M4 Max, Darwin arm64, 128 GiB RAM, Darwin 27.0.
- Toolchain: Go 1.26.6.
- Glippy parent revision: `442935dd30f6b94893c46c40c2973c7eee7adf60`.
- Corpus: `github.com/sqlc-dev/sqlc` at
  `8a7cddfbb9088666eb981645285d7699e71dcb54`.
- Policy: default correctness plus `-Wsuspicious`.
- Module and build caches: task-owned; analysis ran with module lookup disabled.

The profiling run deliberately forced garbage collection and wrote heap
profiles. Its elapsed time and peak RSS are not comparable to the ordinary
performance gate.

## Tier Isolation

Ordinary cold runs used distinct empty Glippy and Go build caches:

| Selection | Elapsed | Peak RSS | Difference from full policy |
| --- | ---: | ---: | ---: |
| correctness plus suspicious | 16.31 s | 3,404,791,808 B | baseline |
| all selected rules except the three SSA rules | 16.28 s | 3,258,597,376 B | -146,194,432 B (-4.3%) |
| all selected rules except `printf-arguments` | 14.61 s | 1,335,197,696 B | -2,069,594,112 B (-60.8%) |

The exact `printf-arguments` rule produced no diagnostics on this revision, but
selecting its wrapper facts still required dependency syntax and type
information. Removing every SSA consumer left more than 3.25 GB resident, so
lazy SSA cannot be the first memory fix for this workload.

Splitting reporter roots alone also does not solve the dependency owner. The
single `./cmd/sqlc` package peaked at 2,968,535,040 bytes because its transitive
fact graph reaches most of the repository and its external dependencies. A
package-wave design must therefore release or summarize dependency graphs; it
cannot merely divide the top-level `./...` match.

Two fresh repetitions kept package-phase heap allocation within
1,484,162,120-1,487,248,320 bytes, source-model heap allocation within
1,600,169,848-1,601,203,544 bytes, and final-result heap allocation within
177,711,648-177,816,096 bytes. The profiles therefore identify a stable owner
rather than one best-sample artifact.

Package loading owns about 1.49 GB of retained heap before Glippy promotes root
files into its complete source model. Source-model construction adds about
113 MB of live heap. Tier execution adds little retained memory after
collection, and the type graph becomes collectible once package analysis no
longer needs it.

The package-phase heap profile attributes the largest flat owners to:

| Owner | Retained heap |
| --- | ---: |
| `go/types.(*Checker).recordTypeAndValue` | 512.08 MiB |
| `go/parser.(*parser).parseOperand` | 133.01 MiB |

The source-model delta is led by source pieces (39.13 MiB), token scanning
(24.89 MiB), physical line indexes (12.53 MiB), and trivia (12.07 MiB). That
cost is bounded to reporter-visible roots and is no longer the first
divergence.

## Resolved Boundary

The follow-up implementation preserves the standard analyzer's wrapper facts
and byte-identical diagnostics without retaining its transitive syntax and
`go/types.Info` graph in the ordinary Glippy process. The CLI now executes the
exact upstream analyzer through a serialized same-binary `unitchecker` process
after the first package graph is released.

The investigation tested:

1. lightweight dependency metadata filtering;
2. dependency-first fact production in bounded package waves;
3. canonical fact snapshots rebound through stable object paths; and
4. isolated exact upstream execution after the ordinary root load.

The in-process wave alternatives remained above the 2 GiB target. Isolated
exact execution reduced the production workload to 1,306,836,992 bytes cold
and 552,550,400-555,696,128 bytes warm while preserving normalized diagnostic
SHA-256 `030f4474aec74877307118376e77e8ad7254a46c32777242fd11e3223c7282d0`.
The complete decision and measurements are recorded in
[`v0.5-printf-fact-execution-2026-08-19.md`](v0.5-printf-fact-execution-2026-08-19.md).
Portable release budgets still require native macOS and Linux evidence.
