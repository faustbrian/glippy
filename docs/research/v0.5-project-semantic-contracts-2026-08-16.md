# v0.5 Project Semantic Contracts, 2026-08-16

## Decision

The v0.5 project semantic-contract boundary is implemented for exact functions
and declared methods already present in an effect-aware typed package graph.
Projects can describe application and dependency behavior that Go export data
does not encode without loading executable plugins or dependency source solely
for contract resolution.

The active effect schema is version 4. Configured records participate in the
same stable identities, scheduling, control-flow predicates, rule contexts, and
persistent-cache invalidation as inferred same-module summaries.

## Supported Contracts

Schema version 1 supports:

- no normal continuation;
- required result use;
- parameter close, ownership-transfer, transaction-completion, and
  cancellation-invocation effects;
- calls that may block;
- nil-capable result states conditional on an exact built-in-error result; and
- results that alias call arguments.

Declarations use exact `package/path.Function` or
`package/path.Type.Method` identities. Import aliases, suffixes, promoted
methods, and naming conventions do not participate in matching.

## Validation And Resource Boundary

Configuration selects at most 32 normalized project-relative files. Reads stay
inside the selected project root, refuse final and directory-component symlink
escapes, and enforce the lesser of the 1 MiB per-file allowance and remaining
4 MiB snapshot allowance before snapshot allocation. The complete snapshot is
limited to 4,096 functions and 64 entries in each indexed relationship.

Parsing is strict and versioned. Unknown fields, malformed TOML, duplicate
files or symbols, empty effects, invalid indexes, conflicting relationships,
and unsupported versions fail. Semantic failures identify their
`[[functions]]` declaration where its physical location is unambiguous.

Resolution validates every loaded package variant sharing a package path.
Referenced results and parameters must exist; nil/error relations require an
error-assignable result and nil-capable value; aliases require compatible
types. Validation order is independent of package-load order. Contracts for
packages absent from a partial graph remain deferred, while a missing symbol in
a present package fails.

## Scheduling And Identity

Contract parsing is configuration work and does not raise the selected analysis
tier. Symbol resolution occurs only when an enabled CFG or SSA rule already
requires effect facts. External functions resolve from loaded export type
information without requesting their source bodies.

Configured parameter and returned-state records take precedence over inference
for the same exact relationship; inference fills only unstated records.
No-return, required-result, blocking, and alias records are additive exact
facts. Contract paths and process-local object pointers do not enter semantic
effect identity.

The immutable snapshot is reused by ordinary package analysis, each configured
CI target, and LSP overlay analysis. Configuration identity includes canonical
paths and contents. The `native-effects-v4` digest includes every resolved
effect so a changed contract invalidates an otherwise warm native result.

## Verification

Focused package tests exercise strict decoding, canonicalization, byte and
declaration bounds, physical error locations, exact function and method
resolution, deterministic package-variant validation, demand-driven signature
checks, configured control-flow facts, external export-only resolution, cache
invalidation, configuration introspection, target-matrix reuse, and LSP overlay
reuse.

The complete repository test suite, vet, module-tidiness check, generated rule
documentation, candidate build, candidate self-check, and diff-hygiene gates
pass on the final batch. No generated rule-documentation drift was produced.

## Deliberate Limits

Contracts assert runtime behavior; Glippy validates structure and signature
compatibility but cannot prove that an assertion is true. Packages absent from
a partial load remain unchecked until a selected typed graph contains them.
Runtime plugins, arbitrary executable configuration, replacement Go types,
receiver effects, generic value relationships, and speculative dependency-body
inference remain outside schema version 1.
