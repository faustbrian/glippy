# v0.5 Memory-Aware SSA Package Waves, 2026-08-19

## Decision

Glippy now builds one bounded `golang.org/x/tools/go/ssa` program at a time.
Canonical selected-package waves admit at most 64 root packages and 8 MiB of
compiled source deduplicated within each package and conservatively charged
again for each selected test variant. One root package exceeding the byte
budget remains eligible alone. Every enabled SSA rule and eligible source
function in one wave shares the same immutable program, and no scheduler-owned
reference to that program survives construction of the next wave.

Compiled-source accounting is package-variant aware. An augmented test package
is charged for the complete production and test source set its SSA program
builds, even when reporter ownership assigns a shared production file to the
ordinary package. Duplicate compiled paths inside one package are charged once.

The runner computes the selected roots' no-return analysis and optional
return-state summaries once before any SSA build. The same immutable predicates
and effect summaries are installed into each wave. Debug mappings remain
demand-driven by the maximum enabled SSA-rule requirement, dependency packages
remain type-backed shells without bodies, and reporter-visible diagnostics keep
canonical ordering across waves.

## Alternatives And Measurement

The previous unbounded program retained every selected root's built SSA
functions until the last package callback completed. A first package-at-a-time
prototype narrowed that lifetime maximally. On this repository, three warm
paired SSA-tier samples reduced median peak RSS from about 765 MB to 729 MB but
increased median elapsed time from about 0.57 seconds to 0.83 seconds. The
roughly 46% latency cost was rejected.

Fixed package counts of 4, 8, and 16 were then compared through fresh baseline
and candidate binaries running only `nilness`, `overwritten-error`, and
`typed-nil-error-return`. Four and eight packages showed only noisy, small RSS
movement with roughly 15-19% warm latency cost. Sixteen packages increased
median RSS in its three-sample run. A seven-sample eight-package follow-up still
showed about 1.6% lower median RSS with about 12% higher median latency. Fixed
CPU-oriented counts were therefore rejected as the primary policy.

The accepted wave uses both actual compiled-source bytes and a high count cap.
This repository remains below both limits and therefore retains one-program
latency. Larger root sets receive a deterministic simultaneous-retention bound.
The directional local samples are design evidence, not portable performance
budgets.

## Behavioral Evidence

The count-bound regression loads 65 independent module packages with two source
functions each. Before the change, all packages observed the same
`*ssa.Program`, and the regression failed. After the change, the first 64
packages share one program and the final package receives a second program;
both functions in every package still observe one shared program, and each
program resolves the package's exact `ssa.Package`.

Pure wave regressions cover count exhaustion, byte exhaustion, compatible
byte packing, and one oversized package remaining eligible alone. Variant
accounting proves that an augmented test package is charged for both its shared
production file and test-only file.

The existing SSA suite continues to prove canonical declaration and function
literal callbacks, shared rule/function identity within a wave, optional debug
mappings, generated-file policy, test-variant ownership, effect-fact return
states, cancellation, and diagnostic validation. Focused nilness,
overwritten-error, and typed-nil suites preserve the admitted rule behavior.

## Boundaries

This batch establishes a representation-lifetime contract, not a measured
release-scale RSS reduction. Recreating dependency shells for each wave can
trade work for lower simultaneous root-program retention, so the 8 MiB and
64-package limits require reevaluation against a pinned large multi-package
corpus before stable release.

`x/tools/go/ssa` exposes supported program and package construction but no
public per-function build-and-release boundary. Glippy does not introduce a
competing SSA builder to claim per-function laziness. Metadata-only workspace
graph discovery and portable macOS/Linux release-candidate budgets remain
separate v0.5 work.
