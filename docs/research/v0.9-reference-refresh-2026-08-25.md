# v0.9 Product Reference Refresh, 2026-08-25

## Decision

Current Oxfmt, Oxlint, Oxc, Clippy, rustfmt, Go vet, and Staticcheck evidence
does not require a Glippy architecture or product-scope change before the v1
contract freeze. Glippy retains one opinionated Go CLI with separate formatter
and linter engines, a shared source and analysis foundation, deterministic
versioned reports, transactional fixes, and no required plugin, hosted,
package-manager, custom-Action, or editor-extension ecosystem.

This refresh is source and product comparison evidence. It does not replace
the exact Glippy corpus, performance, fix-safety, upgrade, or release-candidate
gates.

## Oxfmt, Oxlint, And Oxc

The current Oxc source reviewed for this refresh is commit
[`faf11d9`](https://github.com/oxc-project/oxc/commit/faf11d9d6e566ec3d99d12cdf52fa0c3af9ecf39)
from 2026-08-25. The current published application release is
[`apps_v1.80.0`](https://github.com/oxc-project/oxc/releases/tag/apps_v1.80.0),
which contains Oxfmt 0.65.0 and Oxlint 1.80.0. Current website source was
reviewed at
[`527e98e`](https://github.com/oxc-project/website/commit/527e98e8f302bcbf3545b04f7e110d50b44a51df).

The comparison from the prior Glippy review at Oxc `2dad1e0` covers 76 commits.
The material product evidence is:

- Oxfmt's formatter policy now states that fixture and Prettier conformance
  runs reformat every output to detect idempotency failures and that
  language-specific conformance includes real repositories. This reinforces
  Glippy's byte-idempotency and pinned-corpus gates.
- Oxfmt retains its arena document model, iterative printer, explicit check and
  stdin workflows, nested configuration, and LSP integration. Its CLI still
  writes changed files with ordinary `fs::write`; Glippy retains validated
  same-directory atomic replacement for supported local filesystems.
- Oxfmt 0.65.0 adds formatter and conformance work, including YAML source
  fidelity. None changes the Go grammar, trivia, bounded-rendering, or
  deterministic-layout decisions owned by Glippy.
- Oxlint 1.80.0 adds and corrects individual rules and suggestions. Its CLI
  still separates `--fix`, `--fix-suggestions`, and `--fix-dangerously`, with
  dangerous mode also selecting dangerous suggestions.
- Oxlint's JSON output still includes runtime-dependent `threads_count` and
  `start_time` without an explicit result-schema version. Glippy retains
  deterministic schema-versioned machine output without runtime identity.
- Oxlint's production runtime still writes with ordinary `fs::write`. The
  reviewed fixer and runtime changes do not add Glippy-equivalent stale-source,
  all-participant conflict refusal, release-build reparse, formatter, and
  transactional write validation.
- The Oxc language server can now return multiple configuration messages when
  tools start or restart. This is a useful diagnostics refinement but does not
  invalidate Glippy's existing bounded stdio LSP, configuration diagnostics,
  or shared CLI analysis engine.

No new Oxc evidence supports copying ESLint-compatible configuration and
plugins, enabling every analysis tier eagerly, silently selecting one
overlapping fix, or widening Glippy's reporter catalog without a consumer.

## Clippy

Current rust-clippy source was reviewed at
[`095336b`](https://github.com/rust-lang/rust-clippy/commit/095336b1d5511dd5e81cd3922925a48f8777b662)
from 2026-08-24. The 39-commit comparison from the prior restriction-policy
review at `e8bea03` contains rule maintenance and catalog synchronization but no
change to the inspected lint-level and group surfaces:

- `allow`, `warn`, `deny`, and irreversible `forbid` remain the useful policy
  levels;
- exact lints and coherent groups remain independently selectable;
- correctness-oriented defaults remain distinct from pedantic and restriction
  policy; and
- the complete restriction group remains unsuitable for wholesale enablement.

Glippy therefore retains its Go-native groups, ordered command-line lint
levels, exact-ID restriction rules, baselines, narrow suppressions, and
separate fix safety. Comparable usefulness still does not mean Rust compiler
integration, Cargo lints, macro lints, or rule-for-rule catalog parity.

## rustfmt And gofmt

Current rustfmt source was reviewed at
[`138684c`](https://github.com/rust-lang/rustfmt/commit/138684c5526224e58f8850d7995b2214ec3440e0)
from 2026-08-25. Its current documented product contract still provides file
and stdin formatting, workspace formatting through `cargo fmt`, a non-mutating
`--check` mode, explicit configuration, and a post-1.0 stability policy with
documented exclusions for unsupported or unstable source shapes.

Glippy adopts the stable-output and check-mode lessons while retaining a much
smaller formatter configuration dialect, explicit Go source-version handling,
and its own comment, directive, fragment, and write-safety contracts.

Go 1.27.0 `gofmt`, `go/format`, and `go/printer` remain syntax and differential
authorities, not the width-aware layout ceiling. Glippy's published fixed-point
decision still requires its own idempotency and classifies deliberate gofmt
divergences rather than promising byte compatibility.

## Go Vet And Staticcheck

The current Go comparison is already bound to Go 1.27.0 and
`golang.org/x/tools` v0.49.0 in the
[Go vet compatibility record](../go-vet-compatibility.md). Glippy continues to
adapt suitable analyzers through its own registry, scheduling, configuration,
reporting, suppression, and fix-safety contracts and documents the default vet
analyzers it does not replace.

The current Staticcheck release is 2026.2.1, module version v0.8.1, published
2026-08-21. The pinned public-corpus workflow uses that exact version. Its
findings remain a comparator and rule-gap input; they do not grant Staticcheck
authority over Glippy defaults, ranges, fixes, or profile membership.

## v1 Consequence

The v0.9 freeze should preserve the current product direction:

1. stable formatter output changes require migration evidence;
2. default lint signal remains correctness-focused and corpus-adjudicated;
3. pedantic, performance, complexity, style, and restriction policy remain
   opt-in according to their documented group contracts;
4. fixes retain separate safe, suggestion, and unsafe authorization;
5. one canonical engine owns every CLI, reporter, and LSP result; and
6. public repositories remain immutable validation inputs rather than an
   ecosystem-adoption program.

Revisit this decision when a reference product changes one of the compared
architectural or safety boundaries, when Go frontend capabilities materially
change, or when Glippy evidence demonstrates a missing daily-use workflow.
