# v0.4 Analysis Statistics Evidence, 2026-08-15

## Scope

Glippy v0.4 adds opt-in execution statistics to non-writing `lint` and
combined `check` runs. This record covers the implementation at
`42db8b5fb922bdba9a8c4bd2340f43746c707a2d` plus the uncommitted statistics
batch on Go 1.26.6, Darwin arm64, and an Apple M4 Max.

The observations below are profiling evidence, not a stable latency or memory
budget. Stats mode samples process-wide runtime counters on rule callbacks and
therefore adds substantial overhead. Callback durations may overlap, and
allocation deltas can include concurrent Glippy work. Go-command subprocess
allocations remain outside the process counters.

## Behavioral Evidence

Focused CLI tests prove that `lint --stats=json` and `check --stats=json` keep
diagnostics on standard output and emit one schema-version-1 statistics
document on standard error. Invalid format names, duplicate stats flags,
fixing, fix previews, and baseline generation are rejected. Package-driver
tests prove selected tier and dependency reasons, effect-fact reasons, cold
cache misses and writes, warm cache hits, and zero callbacks on cached native
results. Reporter tests prove canonical rule ordering and visible,
pre-existing, suppressed, and baselined disposition counts.

The complete repository test suite and `go vet ./...` passed with disposable
Go build caches. A freshly built Glippy binary then completed `check ./...`
with no formatting or lint findings.

## Dogfood Observations

Each probe used a freshly built binary, a task-owned Go build cache, a
task-owned XDG cache root, and disabled module lookup. Persistent analysis
caching remained disabled by project policy, so cache counters are zero. The
second run is warm only with respect to operating-system and Go package-loading
state.

| Target and mode | Result | Files | Loaded files | Packages | Total | Package loading | Analysis |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Glippy cold `check` | clean | 251 | 1,902 | 56 | 39.476 s | 2.180 s | 36.038 s |
| Glippy warm `check` | clean | 251 | 1,902 | 56 | 40.029 s | 0.869 s | 37.753 s |
| `pkg/prompts` cold `lint` | clean | 65 | 989 | 6 | 11.600 s | 1.453 s | 10.140 s |
| `pkg/prompts` warm `lint` | clean | 65 | 989 | 6 | 5.840 s | 0.477 s | 5.357 s |

All four runs selected control-flow as the maximum tier. `printf-arguments`
required dependency syntax; `context-cancel-leak` and
`sql-transaction-not-completed` required effect facts. Neither repository
produced a diagnostic, and the `pkg/prompts` tree at
`1b36d9c660ce793bbcd7922d19f853dfa53cbf6f` remained unchanged.

The process-wide total counters observed approximately 42.95 million
allocations and 6.72 GB allocated bytes for each Glippy self-check, and 12.50
million allocations and 1.49 GB allocated bytes for each `pkg/prompts` lint
run. These values include profiling overhead and are useful for comparing the
same stats mode, not for claiming ordinary-run memory usage.

## Limitations And Revisit Triggers

- Persistent cache hit, miss, invalidation, and write behavior is proven by
  the package-driver fixture rather than these cache-disabled dogfood runs.
- Stats mode is deliberately not a release latency benchmark. Stable ordinary
  cold, warm, and peak-resident-memory budgets remain separate release work.
- Per-rule runtime allocation deltas are process-local observations, not
  goroutine-local attribution. Revisit the schema or sampler if Go exposes a
  bounded rule-local allocation mechanism.
- Failure and cancellation suppress the document rather than reporting
  partial measurements. Fix-transaction phase profiling remains deferred.
