# v0.6 `standard-method-signature` Profile Calibration, 2026-08-24

## Decision

Move `standard-method-signature` from `correctness` to `pedantic`. The exact
rule remains available through the pedantic preset or an explicit rule
override, and Glippy continues to document its direct `go vet` `stdmethods`
compatibility.

## Evidence

Pinned Prometheus evidence from corpus run `32662850047` at Glippy revision
`1eb79dba2314706684aa8364e1b1cb25837abed1` produced 26 unique
`standard-method-signature` findings in both default and recommended. Every
finding targets a `Seek(int64) chunkenc.ValueType` declaration or
implementation belonging to Prometheus's documented sample-iterator contract.
None of those methods intends to implement `io.Seeker`, whose unrelated
signature is `Seek(int64, int) (int64, error)`.

The upstream analyzer and `go vet` both report these methods because their
contract uses the method name as its primary intent signal. The analyzer has
no type relationship, assignment, assertion, embedding, or caller evidence
that connects the Prometheus iterators to `io.Seeker`. The earlier two-project
dogfood sample contained no such domain-specific methods and therefore did not
establish correctness-preset precision.

## Observable Contract

The built-in `default`, `recommended`, and `strict` profiles do not select
`standard-method-signature`. The `pedantic` profile and an explicit
`standard-method-signature = "warn"` or `"error"` override continue to run the
unchanged analyzer. Exact diagnostics, source-version eligibility,
generated-file policy, suppression behavior, and fix absence do not change.

## Revisit Trigger

Promote the rule only if general semantic evidence can distinguish intent to
implement a standard interface from a domain-specific same-name method, or a
new broad corpus demonstrates near-zero false positives without such an
inference. Do not add project, path, receiver-name, or test-file exceptions.
