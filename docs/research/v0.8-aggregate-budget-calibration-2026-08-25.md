# v0.8 Aggregate Budget Calibration, 2026-08-25

## Decision

The release campaign's provisional aggregate process-tree peak-RSS ceiling for
the pinned typed workload is 3,221,225,472 bytes. The prior 2,147,483,648-byte
ceiling is rejected by native evidence on three supported runners. The 3 GiB
replacement is not stable release evidence until a complete exact-candidate
campaign passes on all four supported macOS and Linux architectures.

The existing 105-second typed latency ceiling, 90-second formatter latency
ceiling, 2 GiB aggregate formatter peak-RSS ceiling, and 250-millisecond editor
ceiling are unchanged.

## Red Native Evidence

Exact Glippy revision `385d98177845028fd1e3ebbfb8716284d7861a76` ran in
[workflow `32804781727`](https://github.com/faustbrian/glippy/actions/runs/32804781727)
with Go 1.26.5. All 20 editor samples and all five formatter samples completed
within their existing budgets on every native runner. The first typed sample
then produced these release-blocking outcomes:

| Runner | Typed outcome |
| --- | ---: |
| Linux amd64 | 2,238,414,848 B exceeded 2 GiB |
| Linux arm64 | 2,197,422,080 B exceeded 2 GiB |
| Darwin amd64 | 2,255,237,120 B exceeded 2 GiB |
| Darwin arm64 | diagnostic fingerprint changed before budget acceptance |

The largest observed aggregate typed peak was 2,255,237,120 bytes. A 3 GiB
ceiling leaves 965,988,352 bytes, or 42.8%, of headroom over that observation.
The round binary-unit boundary is intentionally conservative because this was
the first four-runner campaign to measure the complete concurrent process tree,
not a regression from a previously stable aggregate threshold.

## Diagnostic Boundary

Darwin arm64 normalized typed output changed from the historical fingerprint
`13f9c3dd006a105196c13f766a1c849a882754b3083979e9386c78cc2fdb53d2` to
`77f989f585934478c95acff13a0671521696ad036b9430f033968bcd203baba7`.
The replacement fingerprint remains unaccepted until the exact normalized
release-workload output is inspected and its diagnostics are adjudicated. The
separately pinned SQLC corpus provides a supporting rule-level comparison but
uses a different source revision and cannot authorize this fingerprint. The
workflow keeps the historical fingerprint until the exact-output review is
complete and now retains that Darwin arm64 output with the raw campaign
artifact.

## Exit Requirement

A fresh exact-revision workflow must complete all five typed samples on every
runner, preserve an adjudicated Darwin arm64 fingerprint, build and execute the
native candidate archives, and pass cross-runner byte-for-byte reproduction.
Only that green campaign can make the 3 GiB ceiling stable release evidence.
