# v0.5 Multi-Target Package Analysis, 2026-08-16

## Decision

The v0.5 CI target-matrix capability is implemented for non-mutating package
analysis. One schema-version-1 configuration can select a bounded set of GOOS,
GOARCH, build-tag, and cgo combinations while preserving deterministic
diagnostics, prerequisite failures, baselines, cache identity, and reporters.

This capability does not authorize target-dependent fixes or multiply LSP
analysis. Those boundaries remain deliberately separate under ADR 0020.

## Implemented Contract

- `[[analysis.targets]]` requires exact GOOS and GOARCH values, accepts sorted
  and deduplicated tags plus explicit cgo state, rejects duplicate identities,
  and is bounded at 32 entries.
- Typed `lint`, combined `check`, and baseline generation execute every target
  in canonical order.
- Equal rule diagnostics, package diagnostics, and captured-source problems
  merge once with sorted target identities. Target-specific results remain
  distinct.
- Text, short, schema-version-1 JSON, GitHub, and SARIF output expose target
  attribution without changing rule IDs or ranges.
- Persistent cache entries remain separated by their existing GOOS, GOARCH,
  tag, and cgo key inputs while one invocation aggregates cache statistics.
- Syntax-only lint remains file-oriented, LSP analysis uses the base
  `[analysis]` selection, and every fix class rejects a matrix before mutation.
- `glippy config show` lists the canonical matrix.

## Behavioral Evidence

Focused package and CLI tests cover target canonicalization and the 32-entry
bound, target-specific and cross-target diagnostics, package/type errors,
source-problem merging and independent ownership, combined-check
non-mutation, syntax-only and LSP policy, fix refusal, baseline generation and
application, cold and warm persistent-cache behavior, statistics aggregation,
and text, JSON, GitHub, and SARIF reporting.

The final implementation tree passed:

- `go test ./... -count=1`;
- `go vet ./...`;
- `go mod tidy -diff`;
- `go generate ./internal/report` with no generated drift;
- a fresh `go build` of `./cmd/glippy`; and
- the built binary's `glippy check ./...` self-check.

Every Go command used a task-owned disposable build cache. No source, cache, or
generated artifact from verification remains outside the tracked change.

## Limits

Targets execute sequentially. This keeps ordering and peak resource use
predictable but does not claim optimal matrix throughput. The analysis host
must provide any toolchain, platform dependency, or cgo compiler required by a
configured target. Unsupported but syntactically valid targets remain ordinary
package-loading errors.

Target identity is intentionally absent from portable baseline entries. The
matrix merges an identical diagnostic before generation, so one entry waives
that structural occurrence across the configured matrix. A target-specific
source or diagnostic retains its own structural identity. Changing matrix
membership still changes canonical configuration and cache identity.

Fix support remains excluded until one transaction can reconcile proposed
edits and validate final bytes across every target. LSP target matrices remain
excluded until an interactive platform-aware journey demonstrates value within
the editor latency and memory budgets.
